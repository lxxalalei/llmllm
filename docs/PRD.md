# 企业产品知识漏斗助手 PRD

## 1. 文档信息

- 产品名称：企业产品知识助手
- 产品形态：企业内部知识生产与问答平台
- 面向规模：约 3000 人企业
- 核心用户：
  - 普通员工：主要使用群体，约数千人
  - 产品 / 测试：几十至数百人
  - 开发人员：几十人
- 当前版本：V1.0 规划稿

---

## 2. 项目背景

企业产品知识目前通常分散在多个来源中：

- 源代码
- 开发文档
- 技术规范
- PRD
- 产品说明
- 测试经验
- FAQ
- 用户口口相传的信息

这些知识之间缺乏稳定关联。

常见问题包括：

1. 代码已经修改，但开发文档、产品说明、FAQ 没有同步更新。
2. 不同角色对同一个功能的理解不同。
3. 普通员工无法理解底层技术文档。
4. 产品和测试遇到问题时，经常需要反复询问开发。
5. 开发需要重新查看代码才能确认历史逻辑。
6. FAQ 依赖人工维护，容易过期。
7. 企业知识库虽然有大量文档，但知识粒度不统一，检索准确率有限。
8. AI 问答无法判断某条知识到底来源于代码、产品设计还是历史经验。

因此，需要建立一套从源代码开始逐层抽象、长期沉淀并持续维护的企业产品知识体系。

---

## 3. 产品定位

本产品不是单纯的 AI FAQ 机器人。

产品定位为：

> 以代码事实为底层依据，通过工程规则、产品逻辑、用户知识逐级抽象，形成长期可维护、可追溯、可检索的企业产品知识体系，并基于用户角色提供不同深度的智能问答服务。

整个产品由两部分组成：

```text
知识生产系统
+
知识消费系统
```

知识生产：

```text
Code
 ↓
L1 工程事实
 ↓
L2 开发规则
 ↓
L3 产品功能逻辑
 ↓
L4 用户知识 / FAQ
```

知识消费：

```text
企业员工
 ↓
身份 / 角色识别
 ↓
分层检索
 ↓
知识问答
```

## 4. 产品目标

### 4.1 核心目标

建立一套统一的产品知识生产链，使：

```text
代码变化
可以最终反映到
用户看到的知识
```

实现：

- 知识长期沉淀
- 知识来源可追溯
- 知识变化可感知
- 知识影响可分析
- 知识更新可持续
- 不同角色看到不同深度的知识

### 4.2 用户侧目标

#### 普通员工

目标：

> 不需要了解技术实现，也能够快速获得准确、明确、可执行的产品答案。

重点解决：

- 功能在哪里
- 功能怎么使用
- 为什么出现某种现象
- 权限为什么不同
- 某个状态是什么意思
- 出现问题应该怎么处理

#### 产品 / 测试

目标：

> 快速获得完整的产品功能逻辑，并在必要时向技术规则下钻。

重点解决：

- 功能完整规则
- 边界条件
- 状态变化
- 权限规则
- 异常逻辑
- 与其他功能的关联
- 当前实现是否符合产品逻辑

#### 开发

目标：

> 快速理解功能背后的开发规则、代码事实和实现位置。

重点解决：

- 某个功能在哪里实现
- 当前开发规则是什么
- 哪些模块有关联
- 修改某段代码可能影响什么
- 产品逻辑来源于哪些实现

---

## 5. 非目标

V1 不重点解决以下问题：

1. 完整代码 Coding Agent。
2. 自动修改代码。
3. 自动执行生产环境操作。
4. 完整企业通用知识库。
5. 完全替代 PRD。
6. 完全替代开发文档。
7. 完全无人审核的产品知识发布。
8. 多 Agent 自由协作。
9. 全公司所有代码一次性接入。

V1 核心目标是验证：

> 能否稳定建立“代码 → 用户知识”的长期知识链路。

## 6. 用户模型

### 6.1 用户层级

| 用户 | 主要知识层 | 用户规模 | 查询特征 |
|---|---|---:|---|
| 普通员工 | L4 → L3 | 1000~3000 | 高频、简单、口语化 |
| 产品 / 测试 | L3 → L2 | 数十~数百 | 中频、规则型 |
| 开发 | L2 → L1 → Code | 数十 | 低频、深度、高专业度 |

### 6.2 核心设计原则

不同角色不维护独立知识库。

统一维护：

```text
L1
L2
L3
L4
```

不同角色只是获得不同的 Knowledge View。

即：

> 同一套知识资产，不同角色的不同视图。

## 7. 知识模型

### 7.1 Source：代码源

代码本身为最底层事实来源。

主要记录：

- Repo
- Branch
- Commit
- File
- Module
- Class
- Function
- API
- Enum
- Config
- Database Field
- Symbol

Source 不属于知识抽象结果，而属于知识来源。

---

## 8. L1：工程事实层

### 8.1 定义

从代码中直接提取出的客观实现事实。

核心原则：

> 描述系统现在实际上是怎么运行的，而不是它应该怎么运行。

### 8.2 示例

代码：

```python
if ticket.status == CLOSED and inactive_days >= 30:
    archive(conversation)
```

L1：

```text
当工单状态为 CLOSED，且连续 30 天无活动时，
ConversationArchiveService 会执行 archive。
```

### 8.3 L1 内容类型

包括：

- 状态判断
- 权限判断
- API 行为
- 数据结构
- 配置项
- 状态转换
- 事件触发
- 调用关系
- 数据读写
- 错误处理
- 模块依赖

---

## 9. L2：开发规则层

### 9.1 定义

从多个工程事实中进一步抽象出的技术规则和领域约束。

面向：

- 开发
- 架构
- 部分测试

### 9.2 示例

```text
工单会话归档统一由 ConversationArchiveService 管理。

工单会话只有在：
1. 工单已结束；
2. 连续30天无有效消息；

两个条件同时满足时才进入归档。
```

### 9.3 L2 内容类型

包括：

- 开发约束
- 生命周期规则
- 模块职责
- 权限规则
- 状态机规则
- 事件规则
- 数据规则
- 接口规则
- 跨模块依赖

---

## 10. L3：产品功能逻辑层

### 10.1 定义

以产品语言描述功能真正的业务规则。

这是整个知识体系的核心中间层。

### 10.2 示例

```text
功能：工单会话自动归档

触发条件：
- 工单已经结束
- 连续30天没有新消息

系统行为：
- 会话从最近会话列表中移除
- 历史消息仍然保留
- 用户可在归档列表中查看
```

### 10.3 L3 主要结构

每个 Product Logic 至少包括：

- 功能名称
- 功能描述
- 使用对象
- 前置条件
- 触发条件
- 系统行为
- 状态变化
- 权限
- 异常情况
- 边界条件
- 与其他功能关系
- 来源

---

## 11. L4：用户知识层

### 11.1 定义

将产品逻辑转换为普通员工能够直接理解和使用的知识。

L4 不仅包括 FAQ，还包括：

- FAQ
- 功能说明
- 使用指南
- 错误解释
- 操作说明
- 权限解释
- 状态解释
- 常见场景
- 术语说明

### 11.2 示例

```text
Q：为什么以前的工单群找不到了？

A：
已经结束并长期没有新消息的工单群会自动进入归档列表。
历史消息不会被删除，可以在归档会话中继续查看。
```

## 12. 知识关系模型

所有知识必须保留来源关系。

典型关系：

```text
Code Symbol
    ↓
L1 Engineering Fact
    ↓
L2 Engineering Rule
    ↓
L3 Product Logic
    ↓
L4 FAQ
```

支持关系：

```text
derived_from
depends_on
related_to
affects
belongs_to
```

示例：

```text
archive_if_inactive()
      ↓
fact.archive.trigger
      ↓
rule.work_order.archive
      ↓
product.auto_archive
      ↓
faq.chat_disappeared
```

## 13. 知识状态

每条长期知识必须具备状态。

V1 使用：

```text
Draft
Review
Published
Outdated
Deprecated
```

### Draft

系统生成，尚未确认。

### Review

等待人工审核。

### Published

正式知识，可进入问答。

### Outdated

底层知识发生变化，当前内容可能已经失效。

### Deprecated

功能已废弃。

## 15. 增量更新流程

代码变化后，不重新生成整个知识库。

流程：

```text
Git Commit
 ↓
Change Detection
 ↓
识别 changed symbol
 ↓
寻找绑定的 L1
 ↓
影响分析
 ↓
沿依赖关系向上传播
```

例如：

```text
30天
↓
修改为
60天
```

系统识别：

```text
L1：需要更新
L2：需要更新
L3：需要审核
L4：可能过期
```

并触发增量知识更新。

## 16. 变更影响分析

系统需要支持：

> 修改了这一处代码，哪些知识可能受到影响？

输出示例：

```text
本次代码修改影响：

L1
- 工单归档触发条件

L2
- 工单会话生命周期规则

L3
- 工单会话自动归档

L4
- 为什么我的工单群消失了？
- 工单群多久会被归档？
- 已归档工单在哪里查看？
```

## 17. 人工审核机制

系统不要求每一级都人工审核。

推荐：

```text
Code → L1
高度自动化

L1 → L2
高度自动化

L2 → L3
关键功能人工审核

L3 → L4
大部分自动生成
```

原因：

> 代码实现不一定等于产品设计。

因此 L3 是最重要的语义审核节点。

## 18. 问答系统

知识生产与问答必须解耦。

不能：

```text
用户问问题
↓
临时读代码
↓
临时生成产品规则
↓
回答
```

应该：

```text
Code
↓
提前生产知识
↓
Published Knowledge
↓
用户查询
```

```text

 ↓

 ↓

 ↓
是否高置信命中？
```

高置信：

```text

↓

```

```text

```

```text

↓

```

```text

```

## 23. 搜索设计

系统采用 Hybrid Retrieval。

包括：

```text
Dense Embedding
+
Sparse / BM25
+
Metadata Filter
+
Rerank
```

### 23.1 为什么需要 Embedding

解决语义相似问题。

例如：

```text
工单聊天怎么没了
```

能够匹配：

```text
为什么工单会话被自动归档？
```

### 23.2 为什么需要关键词检索

企业内部存在大量：

- 功能名
- 产品名
- 按钮名
- 状态
- API
- 类名
- 内部术语

例如：

```text
PMGO
work_order
ConversationArchiveService
```

需要精确搜索。

## 24. FAQ 高置信命中

如果用户问题与标准 FAQ 高度一致，可以直接返回已经审核过的答案。

流程：

```text
Query
 ↓
FAQ Retrieval
 ↓
FAQ Confidence
```

高置信：

```text
直接返回 FAQ
```

不再调用复杂 Agent。

注意：

> 具体阈值不能直接使用固定 embedding score，例如 0.92，必须通过真实企业问题数据校准。

## 32. 技术建议

当前建议技术基线：

| 模块 | 技术 |
|---|---|
| Backend | Python + FastAPI |
| Workflow | LangGraph |
| Code Parser | Tree-sitter |
| Schema | Pydantic |
| Knowledge Asset | Markdown + YAML |
| Asset Version | Git |
| Relation / Metadata | PostgreSQL |
| Search | Qdrant |
| LLM | Provider Adapter |
| Cache | Redis，按需 |
| Auth | 企业 SSO / IAM |

技术选型原则：

- LangGraph 负责知识生产与更新编排，不定义业务知识模型。
- Qdrant 负责检索索引，不作为知识权威数据源。
- PostgreSQL 负责知识元数据、关系、版本和来源绑定。
- Git + Markdown/YAML 保存长期、人工可读的知识资产。
- Agent、模型、向量数据库均应保持可替换。

## 33. V1 范围

一期不要直接接整个企业。

选择一个真实业务模块，例如“工单会话”，完成完整闭环。

### Step 1

读取真实代码。

### Step 2

生成约：

```text
10~30 条 L1
```

### Step 3

抽象：

```text
3~10 条 L2
```

### Step 4

形成：

```text
3~10 个 L3 Product Logic
```

### Step 5

形成：

```text
10~30 个 L4 FAQ
```

### Step 6

上线三角色问答。

### Step 7

修改一处代码。

### Step 8

验证：

```text
是否能识别受影响 L1
是否能定位相关 L2
是否能标记 L3
是否能定位受影响 FAQ
```

## 34. V1 验收标准

### 34.1 知识链路

至少一个模块完整实现：

```text
Code → L1 → L2 → L3 → L4
```

且能够反向追溯。

### 34.2 知识更新

修改已绑定代码后，系统能够自动识别相关知识可能过期。

### 34.3 普通用户问答

测试集中的常见问题：

FAQ / 产品知识正确命中率达到可上线标准。

具体指标应通过真实测试集确定，不提前拍固定数字。

### 34.4 角色隔离

普通用户不能检索：

```text
L1
L2
Code
```

### 34.5 来源

产品 / 开发用户能够查看答案的知识来源。

## 36. 长期规划

最终 L3 Product Logic 不只生成 FAQ。

可以继续派生：

```text
                    Product Logic
                         │
      ┌──────────────────┼──────────────────┐
      ↓                  ↓                  ↓
     FAQ              Test Case         User Guide
      │                  │                  │
      ↓                  ↓                  ↓
客服知识             自动测试知识        产品帮助中心
```

进一步可以生成：

- 产品手册
- 培训资料
- 测试用例
- Release Note
- API Guide
- 操作说明
- 客服回复

最终形成：

> 一个以产品逻辑为中心、代码事实为底座、面向不同企业角色持续发布知识的 Product Knowledge Platform。

## 37. 产品核心原则

### 1. Knowledge First

知识资产比 Agent 更重要。

### 2. Build Once, Serve Many

复杂知识提前生产，高频用户低成本消费。

### 3. Code Is Evidence, Not Product Truth

代码是重要事实来源，但不自动等于产品设计。

### 4. Product Logic Is Core

L3 是整个系统最核心的知识中间层。

### 5. Traceable

任何关键知识都能够追溯来源。

### 6. Incremental

代码变化后增量更新，而非全库重建。

### 7. Role-based Retrieval

权限控制发生在检索层，而不是 Prompt 层。

### 8. Framework Replaceable

LangGraph、Qdrant、LLM 均属于基础设施。

核心资产始终是：

```text
KnowledgeItem
KnowledgeRelation
KnowledgeVersion
Knowledge Asset
```

---

## 38. 一句话产品定义

> 企业产品知识助手是一套从代码事实持续编译出开发规则、产品逻辑和用户知识，并基于角色向企业员工提供可信、可追溯产品问答的知识生产与服务平台。
